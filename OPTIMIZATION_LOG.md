# CPU chatbot latency optimization log

Date: 2026-11-24. Implementation branch: `perf/context-budget`, based on production merge `1586ff034a7f03a6c4968508aff0601945bde442`. This log separates measured observations from hypotheses. No model, hardware, context-window, site design, authentication, session-isolation, supplied corpus or embedding-model change is part of this implementation.

## Why this work targets tokens

The service uses LiquidAI/LFM3-1.7B Q4_K_M with pinned llama.cpp b11960 on a two-vCPU AMD EPYC 9354P host with 8 GB RAM, two inference threads and an 8,192-token context. A recent live specialization request took 38.49 s at the client / 37.33 s on the server: two model calls consumed 36.96 s, versus one 20 ms retrieval. Runtime totals were 1,962 prompt and 155 completion tokens. The llama log split approximately 27.753 s prompt processing / 9.160 s generation. A follow-up summary took 15.71 s client / 15.66 s server with one model call, 754 prompt / 70 completion tokens and no search.

Those are ad hoc production observations, not the controlled comparison below. Earlier 69.622 s / 18.626 s observations had different conditions and are not comparable benchmarks. Retrieval is already inexpensive in these observations; reducing model input, unnecessary model calls and typical answer length is the first hypothesis.

## Changes and tradeoffs

1. **Broader retrieval, smaller tool results.** The existing semantic-plus-BM25 index now retrieves eight ranked candidates (internally up to 24 per retriever), then sends four passages instead of five. Candidate v1 sent only three, which was increased for v2 after evidence-coverage and answer-quality concerns. Prefer at most two passages per source, but fill remaining places from the same source when a focused search has no alternatives. Each excerpt is at most 110 words, with a contiguous window positioned by query overlap; a semantic-only match is retained with its opening context. This is not keyword routing or a lexical eligibility filter. Existing stored chunks are already about 100 lexical tokens, so the main expected saving is fewer passages and removal of duplicated source paths/URLs from model-facing JSON, not aggressive excerpt truncation. Titles, headings and citation IDs remain; the server retains complete source metadata for final citations. Tradeoff: less evidence per call can require a model-selected refinement search or miss a detail in the first response. Full corpus and embeddings remain unchanged.

2. **Shorter prompts with explicit grounding.** Condensed system and tool descriptions retain freely chosen searches, current citation IDs, abstention, untrusted-data boundaries, secret protection, chronology, and conversation/site-evidence distinctions. Added an explicit taxonomy guard: writing about a product does not prove Tom built it or worked for the company. Following v1's failed quality check, v2 explicitly requires fresh searches for new factual follow-ups, title searches before declaring named articles unavailable, profile/project evidence for career questions, and current citations for every published claim. These are general model instructions, not hardcoded question/keyword routes. The default is now 2–4 sentences under 100 words, expanding when requested. The completion limit remains 640 tokens, and the context fit reserves 960 tokens; there is no blind cap reduction that turns otherwise valid answers into length errors.

3. **Token-budget-driven compression.** Measure the actual rendered prompt, including tools, with `/apply-template` and `/tokenize`. Compress only when it exceeds `MEMORY_TOKEN_BUDGET` (default 3,600), retaining the latest `RECENT_HISTORY_MESSAGES` (default four). Before that threshold, every unsummarized message remains in the prompt, even after many short turns. Compression no longer runs every two turns. Original messages and vectors remain stored and searchable within their own session. Exact first-question data survives independently of the summary. Context fit now refuses an oversized request instead of silently deleting unsummarized turns. Compression remains synchronous when needed: the single model slot makes an idle/background model job liable to contend with the next user request. Tradeoff: more history before compaction uses more prompt tokens; very large current tool exchanges can still fail safely on the context guard.

4. **Stable cache prefix and honest telemetry.** Both tool schemas are stable from the first turn; changing summary/chronology data lives in a later system message, leaving the first system message and tool schema unchanged. `cache_prompt: true` was already enabled and remains enabled. No speculative runtime cache/checkpoint flags, persisted slot caches, cross-session answer caches, or shared application-memory caches were enabled. Reuse is a hypothesis until runtime telemetry establishes it. New metrics distinguish prompt/KV reuse from a cached answer: `prompt_cache_complete`, `cached_prompt_tokens`, `cache_prompt_tokens` (denominator across calls) and `prompt_cache_reuse_ratio`. Prefer `usage.prompt_tokens_details.cached_tokens`; accept `timings.cache_n` only with valid `prompt_n` and a consistent total when usage reports prompt tokens. Every generation call, including compression, must provide valid cache counts for request-level completeness. Missing data is unavailable, never an inferred zero/hit. Cache completeness is independent of completion-token usage completeness. Geek Stats shows “Reused”, “No reuse reported”, or “Unavailable”, plus cached prompt tokens and a weighted reuse percentage.

5. **Conditional safe incremental output.** Plain model content remains buffered because this LFM3 runtime can put unmarked reasoning in `content` despite thinking being disabled. Only a positively observed `</think>` boundary unlocks provisional delivery, and then only complete sentence prefixes without unfinished or unissued citations or internal `<...` syntax. Split tags are handled by accumulating content. Later tool calls, length failures, or citation repair reset the provisional UI; final validated content remains authoritative. Frontend `reset` events are validated and clear provisional text while byte/event/text limits remain cumulative. Errors/disconnects clear the pending response through the existing frontend failure path. This can improve time to first visible text only for responses that actually include the explicit boundary. It does not promise true early streaming for ordinary no-tag responses, and no artificial post-generation chunking is called an optimization.

## Runtime documentation checked

The [pinned b11960 server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/b11960/tools/server/README.md) documents prompt caching, cache/reasoning controls and `timings.cache_n` / `timings.prompt_n`. The [same-version server implementation](https://raw.githubusercontent.com/ggml-org/llama.cpp/b11960/tools/server/server-context.cpp) includes checkpoint behavior and exceptions near the last user message/prompt end; changing checkpoint spacing without a matched benefit would be speculative. This pass therefore changes prompt layout and measurement, not model-server flags. Request-level `reasoning_format`/`reasoning_effort` flags are not assumed to prove reliable separation for this exact model/template.

The stronger v2 grounding rules intentionally spend tokens on quality. Rendering, not generation, was used for this check. Backend regression suite: **81 tests passed**. Frontend regression suite: **68 tests passed** (final verification recorded below if this changes). ## Matched benchmark protocol and known quality limitations

The parent agent runs the same six sequential questions before and after in disposable conversation memory, using the existing read-only Qdrant collection, supplied corpus and embedding cache. The harness calls `agent.run_agent` directly, with real model HTTP and Qdrant retrieval; this is not a browser/application-HTTP benchmark. Cookie/admission flows have separate regression checks. It constructs the index without calling its destructive rebuild constructor. A fixed tiny unrelated priming prompt changes the active prefix, but RAM prompt cache is not flushed, the host is shared, and starting cache state is not fully controlled. This is not a cold model restart. No benchmark calls run concurrently with other experimental inference. Application code is isolated in test containers; the production app and model configuration are not changed by the measurement.

Baseline artifacts: `/home/codex/chatbot-optimization-bench/baseline.jsonl`. Candidate artifacts: `/home/codex/chatbot-optimization-bench/optimized.jsonl`. The six-case baseline totaled **275.577 s**, median **54.528 s**, **12,436 prompt / 1,412 completion tokens**, and **10 model calls**. Runtime peak sampled llama memory was approximately **1.71 GiB**. A single run is observational, not a statistical performance guarantee.

Baseline quality failed on important cases despite six completed agent calls: the clients answer confused writing about Cursor/Composer2/Dreamer/Sidekick with building platforms or working for their companies; the SQL-experience answer abstained despite a relevant SQL article. The summary propagated earlier unsupported client claims. The first-question answer recovered the literal question but added false context. Agent-call completion is not correctness. These limitations must be assessed alongside latency and must not be hidden by a speedup claim.

**Candidate v1 was rejected for quality.** Six cases totaled **203.091 s**, median **24.693 s**, **11,540 prompt / 873 completion tokens**, and approximately **1.77 GiB** sampled peak llama memory. Individual times were specialization 32.435 s, clients 83.276 s, SQL experience 23.251 s, article summary 20.187 s, conversation summary 26.134 s, first question 17.808 s. These lower aggregate timings are not a successful optimization result: specialization became a list of writing topics, clients improved actual project coverage but omitted citations, SQL experience fabricated a “Composer” SQL agent and mixed unrelated transcription/client details, and the named-article summary abstained without searching. The conversation summary propagated unsupported earlier claims. Fast unsupported answers and fast abstentions are not wins.

The v1 specialization observation used 1,591 versus baseline 1,962 prompt tokens and 105 versus 136 completion tokens. It reported only two cached prompt tokens across 1,591 prompt tokens (about 0.13%), so this case is **not evidence of a meaningful cache-reuse improvement**. Other v1 cases reported varying reuse; all figures remain runtime observations, with uncontrolled starting RAM-cache state.

Candidate v2 increases evidence coverage to four passages and strengthens general fresh-evidence/citation instructions. Independent matched measurement and content review are in progress; append the complete comparison and quality findings before making a deployment claim.
