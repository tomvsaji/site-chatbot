# CPU chatbot latency optimization log

Date: 2026-11-24. Implementation branch: `perf/context-budget`, based on production merge `1586ff034a7f03a6c4968508aff0601945bde442`. This log separates measured observations from hypotheses. No model, hardware, context-window, site design, authentication, session-isolation, supplied corpus or embedding-model change is part of this implementation.

## Why this work targets tokens

The service uses LiquidAI/LFM3-1.7B Q4_K_M with pinned llama.cpp b11960 on a two-vCPU AMD EPYC 9354P host with 8 GB RAM, two inference threads and an 8,192-token context. A recent live specialization request took 38.49 s at the client / 37.33 s on the server: two model calls consumed 36.96 s, versus one 20 ms retrieval. Runtime totals were 1,962 prompt and 155 completion tokens. The llama log split approximately 27.753 s prompt processing / 9.160 s generation. A follow-up summary took 15.71 s client / 15.66 s server with one model call, 754 prompt / 70 completion tokens and no search.

Those are ad hoc production observations, not the controlled comparison below. Earlier 69.622 s / 18.626 s observations had different conditions and are not comparable benchmarks. Retrieval is already inexpensive in these observations; reducing model input, unnecessary model calls and typical answer length is the first hypothesis.

## Changes and tradeoffs

1. **Broader retrieval, smaller tool results.** The existing semantic-plus-BM25 index now retrieves eight ranked candidates (internally up to 24 per retriever), then sends four passages instead of five. Candidate v1 sent only three, which was increased for v2 after evidence-coverage and answer-quality concerns. Prefer at most two passages per source, but fill remaining places from the same source when a focused search has no alternatives. Each excerpt is at most 110 words, with a contiguous window positioned by query overlap; a semantic-only match is retained with its opening context. This is not keyword routing or a lexical eligibility filter. Existing stored chunks are already about 100 lexical tokens, so the main expected saving is fewer passages and removal of duplicated source paths/URLs from model-facing JSON, not aggressive excerpt truncation. Titles, headings and citation IDs remain; the server retains complete source metadata for final citations. Tradeoff: less evidence per call can require a model-selected refinement search or miss a detail in the first response. Full corpus and embeddings remain unchanged.

2. **Shorter prompts with explicit grounding.** Condensed system and tool descriptions retain freely chosen searches, current citation IDs, abstention, untrusted-data boundaries, secret protection, chronology, and conversation/site-evidence distinctions. Added an explicit taxonomy guard: writing about a product does not prove Tom built it or worked for the company. Following v1's failed quality check, v2 explicitly requires fresh searches for new factual follow-ups, title searches before declaring named articles unavailable, profile/project evidence for career questions, and current citations for every published claim. These are general model instructions, not hardcoded question/keyword routes. The default is now 2–4 sentences under 100 words, expanding when requested. The completion limit remains 640 tokens, and the context fit reserves 960 tokens; there is no blind cap reduction that turns otherwise valid answers into length errors.

3. **Token-budget-driven compression.** Measure the actual rendered prompt, including tools, with `/apply-template` and `/tokenize`. Compress only when it exceeds `MEMORY_TOKEN_BUDGET` (default 3,600), retaining the latest `RECENT_HISTORY_MESSAGES` (default four). Before that threshold, every unsummarized message remains in the prompt, even after many short turns. Compression no longer runs every two turns. Original messages and vectors remain stored and searchable within their own session. Exact first-question data survives independently of the summary. Context fit now refuses an oversized request instead of silently deleting unsummarized turns. Compression remains synchronous when needed: the single model slot makes an idle/background model job liable to contend with the next user request. Tradeoff: more history before compaction uses more prompt tokens; very large current tool exchanges can still fail safely on the context guard.

4. **Stable cache prefix and honest telemetry.** Both tool schemas are stable from the first turn; changing summary/chronology data lives in a later system message, leaving the first system message and tool schema unchanged. `cache_prompt: true` was already enabled and remains enabled. No speculative runtime cache/checkpoint flags, persisted slot caches, cross-session answer caches, or shared application-memory caches were enabled. Reuse is a hypothesis until runtime telemetry establishes it. New metrics distinguish prompt/KV reuse from a cached answer: `prompt_cache_complete`, `cached_prompt_tokens`, `cache_prompt_tokens` (denominator across calls) and `prompt_cache_reuse_ratio`. Prefer `usage.prompt_tokens_details.cached_tokens`; accept `timings.cache_n` only with valid `prompt_n` and a consistent total when usage reports prompt tokens. Every generation call, including compression, must provide valid cache counts for request-level completeness. Missing data is unavailable, never an inferred zero/hit. Cache completeness is independent of completion-token usage completeness. Geek Stats shows “Reused”, “No reuse reported”, or “Unavailable”, plus cached prompt tokens and a weighted reuse percentage.

5. **Conditional safe incremental output.** Plain model content remains buffered because this LFM3 runtime can put unmarked reasoning in `content` despite thinking being disabled. Only a positively observed `</think>` boundary unlocks provisional delivery, and then only complete sentence prefixes without unfinished or unissued citations or internal `<...` syntax. Split tags are handled by accumulating content. Later tool calls, length failures, or citation repair reset the provisional UI; final validated content remains authoritative. Frontend `reset` events are validated and clear provisional text while byte/event/text limits remain cumulative. Errors/disconnects clear the pending response through the existing frontend failure path. This can improve time to first visible text only for responses that actually include the explicit boundary. It does not promise true early streaming for ordinary no-tag responses, and no artificial post-generation chunking is called an optimization.

## Candidate v3: model-selected scope with an enforced grounding step

V3 requires a tool call on the initial generation (`tool_choice: required`); the model still freely selects `search_site` or `search_memory` and writes the query. Subsequent calls use `auto`, then `none` after exhausting the configured search budget. This removes reliance on prompt-only compliance without adding keyword/question routes. Tool descriptions restrict memory to what this user/assistant conversation said, and direct questions about Tom's work/articles to published evidence. At least one allowed tool must execute successfully before a final answer is accepted; malformed/unknown calls alone do not satisfy grounding. Empty valid lookups still count as retrieval attempts, not proof of facts.

Tradeoff: even a history-only question or greeting now needs a tool-selection round before answering. That adds a model round trip compared with an allowed direct reply, and current memory results may duplicate messages already visible in the prompt. This cost is intentional in v3 to prevent fast answers that skipped their evidence requirement; it must be measured rather than described as an automatic latency gain. If memory duplication proves significant, returning compact “all messages already visible” metadata when no archive exists is a possible later experiment, not part of frozen v3.

The default search budget changes from three to **two**, retaining one refinement. Normally this bounds the answer/tool loop to three model calls; the existing single citation-repair allowance can add a fourth, and token-budget compression can independently add its call. Environment overrides remain supported. The 640-token completion cap, 8K context, model, authentication, corpus and embeddings remain unchanged.

After site results, a short system reminder lists current citation IDs and asks for supported claims with those IDs. An uncited site answer gets one repair attempt. If evidence is insufficient, the model may return exactly **“I couldn't find that in Tom's published site data.”** without citations. A second uncited noncanonical response fails with a clear application error; it is never silently rewritten into an abstention or saved as a valid answer. Memory-only conversation replies remain source-free. Once any site lookup succeeds, a later memory lookup does not bypass the citation rule. This exact output protocol validates response form, not user-question keywords, and citation presence still cannot prove that a claim is semantically supported.

Provisional site output after an explicit reasoning boundary is also held until a complete prefix contains at least one valid current ID; memory-only prefixes need no citation. Initial required-tool generations never stream answer text before a successful retrieval. Existing reset and incomplete/unissued-ID guards remain.

The [pinned common/chat.cpp parser](https://raw.githubusercontent.com/ggml-org/llama.cpp/b11960/common/chat.cpp) recognizes `required` as a tool-choice mode. Actual LFM3 required-tool grammar behavior must be verified in a bounded parent-run runtime probe before the full matched benchmark. No inference experiment was run by the implementing agent for v3.

V3 backend regression suite: **88 tests passed**, log `/tmp/chatbot-backend-optimization-v3-tests.log`. Added checks cover required → auto → none selection, a two-search refinement limit, no-tool/invalid-tool failures, fresh current-ID reminders, no-ID repair, exact abstention, repeated uncited failure without persistence, memory-only summaries, no memory bypass after site retrieval, and site-prefix citation gating. Frontend product code is unchanged from the previously passing 68-test cache/reset implementation. Runtime quality/latency review remains pending.

The stronger tool-scope descriptions cost more than v2's 559-token prompt. Stable prefix and reduced later payloads remain separate hypotheses/measurements. `/tmp/chatbot-prompt-probe-v3.py` uses template/tokenizer endpoints only and confirmed multiple-system-message context preservation.

## Candidate v4: bounded selection, final-answer continuation and visible-history deduplication

V3 was rejected after three of six calls failed: specialization returned an invalid final response after exhausting two searches (66.193 s); conversation summary exhausted its 640-token response allowance (54.819 s); first-question recall also exhausted 640 tokens before executing a tool (53.943 s). Clients improved to a cited answer (45.548 s), but isolated improvements do not justify deploying a three-failure run. The parent preserves image/artifact snapshots and adds diagnostic lengths/finish flags/tag-presence booleans without logging private reasoning strings. Raw tool syntax is never stripped and repackaged as an answer.

The v3 sequence totaled **336.063 s**, including failed calls. SQL experience completed in 56.907 s and article summary in 58.653 s. Only **three of six** agent calls completed successfully; success counts still do not establish factual correctness.

V4 limits the **initial required-tool selection** to 192 generated tokens, with schema and execution bounds of 1–240 characters for a freely composed query. Full article titles fit this limit. This is a separate tool-selection-stage budget, not a reduction of the unchanged **640-token answer budget**. It bounds runaway tool argument generation; an unusually long selection can now fail earlier rather than consume a full answer allowance.

After every tool round, a concise **user** control message repeats the original question as quoted data, the 2–4 sentence / under-100-word default (unless detail was requested), and model-selected scope rules. Site lookups list current IDs and canonical abstention; memory-only lookups use the visible conversation and retrieved memory as discussion, not independent site facts. These replace late system turns. A template-only probe confirmed the old system reminders rendered as separate system turns after tool responses; whether that caused v3 failures is a hypothesis, not a demonstrated diagnosis.

At search-budget exhaustion the next request **omits tool schemas entirely**, retains native tool-call/result history, and includes a short user instruction that no tools are available. It retains current-ID/canonical-abstention validation. Merely setting `tool_choice: none` while advertising tools is no longer used for forced finalization. Omitting the schema renders successfully with pinned native history; generation improvement still requires matched measurement. Changing the schema at this terminal stage can sacrifice prefix reuse, trading that possibility for a cleaner final-answer request.

When `summarized_to == 0`, every stored message is already in the prompt. A model-selected `search_memory` now returns only `all_messages_visible: true`, message count and the exact first-user anchor. It avoids duplicate passages and embedding lookup; it does not omit any history from usable context. Archived sessions continue the original private hybrid search with chronological options, exact first anchor, and citation stripping. This saves memory-tool input tokens without changing how the model selects scope or query.

The standalone chat page now preserves provisional text/claims when progress status arrives and clears both buffers/content on reset. Existing error cleanup removes failed provisional replies. The actual `static/app.js` was exercised with delta/status/claim/reset/final/error sequences in a minimal Node VM DOM harness: `/tmp/chatbot-static-stream-test.mjs`; all assertions passed.

Final v4 backend regression suite: **91 tests passed**, log `/tmp/chatbot-backend-optimization-v4-tests.log`. Production and development Compose configurations validate successfully; `git diff --check` is clean. Added coverage verifies initial selection 192 versus final answer 640 tokens, aligned schema/execution query limits, user-role original-question/brevity cues, schema omission at exhaustion, no duplicate visible memory search, and unchanged private archived lookup. Parent-run v4 benchmarking evaluates a **container-only `MAX_AGENT_SEARCHES=1` override** as a possible faster site setting; the general source default remains two. A one-search profile sacrifices refinement and is not selected for deployment until answer review supports it.

### Separately bounded runtime RAM prompt cache

The [pinned runtime documents `--cache-ram`](https://raw.githubusercontent.com/ggml-org/llama.cpp/b11960/tools/server/README.md) in MiB, with an 8,192 MiB default. The model container is limited to 2,500 MiB, and sampled peaks grew approximately 1.83 → 1.90 → 2.04 → 2.23 GB over successive benchmark sequences. The original shared RAM cache was not flushed, so this trend cannot be attributed entirely to app-code changes.

Production Compose now specifies `--cache-ram ${LLM_PROMPT_CACHE_MIB:-256}` and the environment example documents 256 MiB. Development Compose has no separate model service; it uses the production model over the external network and inherits this bound. This is a resource bound on optional RAM prompt caching, **not** a claimed latency improvement or a cap on total model memory. It can evict reusable cache entries and increase later prefill work. No checkpoint tuning, disk slot cache, new model or expanded context is introduced. The parent compares candidate app behavior on the original runtime first, then evaluates the capped runtime separately after rollout; do not combine the two changes into an unsupported causal speed/memory claim.

V5 replaces **only the first selection step** with that proven layout. The same LFM3 model chooses `name` (`search_site` or `search_memory`), its own 1–240 character query, chronological order and role in a strict JSON-schema response. It receives the current question last plus only two recent messages, each bounded to 400 characters, as untrusted reference hints. Those hints are not site evidence; full retained history, summary and exact first-question data remain available to answer generation and the private memory tool. This smaller planning view can miss a distant reference, a tradeoff to review alongside routing correctness.

Code requires a complete stop-finished JSON object with exactly the allowed fields, scope/enums and query bounds. It rejects unknown fields/tools, malformed JSON, reasoning-prefixed JSON and truncated plans without salvaging a partial plan or leaking text. A deterministic wrapper marshals the validated choice into the existing allowlisted executor/native tool-history shape. It does not choose scope by keywords, create queries through hardcoded question routes, add a second model, or pretend the first step is an API-native function call. Subsequent native refinement/answer generation and schema-free forced finalization remain as in v4.

Planning uses the ordinary measured nonstreaming `post('chat')` path, so its actual runtime token usage, cache counts and wall time are included in Geek Stats. It permits **192 planning tokens** while answer generation retains **640**. Because planner and answer prompts differ, a stable answer prefix is not a promise of cross-stage cache reuse. The parent benchmarks the full v5 sequence with a container-only one-search setting on the original model runtime before separately testing the new RAM-cache bound.

Citation repair now repeats the same original-question, brevity and evidence instruction as ordinary finalization. It offers refinement only when a search remains; exhausted-budget repair says no tools are available and omits schemas. The one-retry, canonical-abstention and never-save-repeated-uncited-prose rules remain intact.

## Candidate v6: model-selected document groups before hybrid retrieval

Work resumed on 2026-11-26 from the persisted v6 patch after the earlier usage limit interrupted testing; no existing work was reset. The v5 six-case run completed operationally in **218.527 s**, with per-case times **31.327, 39.120, 37.026, 46.066, 35.841 and 29.147 s**. It was **rejected for quality** despite all six agent calls completing. The specialization answer claimed that Tom built the Cursor model and cited his Composer article. SQL/article answers had citations, and conversation summary/recall worked operationally, but the summary propagated the initial false claim. These results do not establish an acceptable latency improvement over the older 275.577 s baseline.

The captured specialization query was “What does Tom specialize in?” Its four selected passages covered a facts-page scale section, a Composer training article, facts-page contact information and an about-page governance section; identity/focus information was absent. This traced a concrete evidence-selection problem: a third-party product's training description could enter a career answer and be misattributed to Tom. More generic grounding prose and merely checking that an issued citation exists did not prevent that failure.

V6 adds `source_type` to the same model's strict initial plan and as an optional argument to native `search_site` refinements. The model chooses the group from semantic intent while still composing its own query:

- `profile`: general identity, career, specialization or client overviews. Exact existing document IDs are `tom-facts.md`, `site-home.md`, and `site-about.md` (the corpus does not call the facts file `site-facts.md`).
- `writing`: a named article or the writing catalog, using `site-writing.md` and documents under `posts/`.
- `all`: specific technical experience or implementation where both profile/project and first-hand article evidence may matter, mixed scope, or uncertainty. This remains the default when a native refinement omits the optional group.

These are document-metadata groups, not hardcoded question/topic routes. No retrieval branch examines words in the query, and no special technical-topic keyword is embedded in the planner rule. A memory plan still chooses private conversation retrieval; its unused document-group field is validated and then omitted from memory arguments.

Both retrieval branches restrict candidates **before reciprocal-rank fusion**: Qdrant uses `MatchAny` on the already-stored `source` payload, and BM25 ranks only chunks in the selected document group. Exact-source restrictions, when used, intersect with that group. Broad retrieval of eight candidates and delivery of four compact passages remain unchanged within the chosen scope. No corpus rewrite, embedding change, re-embedding or vector-index rebuild is needed. The [official Qdrant filtering documentation](https://qdrant.tech/documentation/search/filtering/) describes `MatchAny` as matching one of several keyword values; the existing server version supports it.

Tradeoffs: the extra plan field/instructions cost tokens, and choosing the wrong group can exclude useful evidence. Specific technical experience deliberately permits `all`, since limiting every experience question to profile pages could hide first-hand implementation articles. Newly added profile pages require metadata-group maintenance; unrelated new files remain available through `all`. Filtering reduces the demonstrated opportunity for third-party writing to contaminate general career answers, but it does not prove the model will always select the right group or interpret evidence correctly. Matched answer-level review remains required.

The new tests load the real retrieval module under an isolated import name because HTTP tests intentionally install a `vector_store` stub. They construct `HybridIndex` with `__new__`, use a fake Qdrant client, and never invoke its destructive rebuild constructor. Tests check profile exclusion of articles, writing inclusion of catalog/posts, both pre-fusion candidate filters, unchanged `all` behavior, exact-source/group intersection, invalid-group rejection, planner forwarding, and ignoring the group for conversation memory. Queries deliberately vary across technical, career and unrelated wording to demonstrate that the supplied group, not a query-keyword branch, controls retrieval.

For the final Nov 26 comparison, the parent is establishing a **new isolated baseline and candidate on the same model/version/weights, two threads, 8K context and 256 MiB optional RAM prompt cache**. That comparison must be reported separately from earlier shared-runtime runs whose cache state accumulated across candidates. Production remains unchanged during this evaluation; the implementing agent runs mocked tests only and performs no live inference.

V6 verification: **101 backend tests passed** in 6.321 s, with log `/tmp/chatbot-backend-optimization-v6-tests.log`. The portable standalone stream test passed **1/1**, log `/tmp/chatbot-static-stream-v6-tests.log`. Production/development Compose configurations validate and `git diff --check` is clean. ## Candidate v8: one semantic action and scope-specific answer context

The v7 focused planner preflight failed **four of five scope checks**: technical/article cases selected profile, conversation summary/recall selected site/profile, and first-question recall copied a previous question rather than the current one. The client action selected profile but its query was still meta-instruction text. The parent repeated the same control with **`cache_prompt: false`** and observed the same four-of-five failure pattern. This control did not support prompt-cache corruption as the explanation for these routing failures. Cache behavior can still affect latency; this experiment only addresses the observed semantic regression.

The earlier four-field v5 planner had selected conversation memory correctly, while v6/v7 introduced a fifth independent `source_type` field and showed strong profile bias. This is regression evidence, not proof that field count alone caused it. V8 removes that cross-product decision and returns to four fields: **`action`, `query`, `order`, `role`**. A single model-selected action maps deterministically to the existing executor:

| Model action | Executed tool | Source metadata scope |
| --- | --- | --- |
| `search_profile` | `search_site` | profile |
| `search_writing` | `search_site` | writing |
| `search_site` | `search_site` | all published sources |
| `search_memory` | `search_memory` | this private conversation |

The mapping inspects the explicit selected action, never query words. Native later refinements retain the existing optional `source_type` argument. Scope guidance remains semantic: general identity/career/client overview, named writing/catalog, technical experience needing both source types, or conversation history/unclear reference-only questions. No fixed FAQ query patterns are introduced.

Planner context now contains **only the previous user question, bounded to 240 characters**, as untrusted reference data. It omits assistant prose and earlier messages so previous generated claims cannot contaminate query selection. The current question remains a standalone last user message; exact chronology and full retained conversation remain available later to the memory tool/answer stage. This narrower reference view may not resolve a distant pronoun or a reference to an assistant's numbered list. Such a reference can select memory; the default two-search setting can refine afterward, while a one-search profile trades that flexibility for latency.

Once the initial model plan chooses published-site evidence, v8 also packs the **factual answer** prompt differently: stable system rules, current question, the model-resolved tool query and current retrieval results. It omits historical assistant prose, compressed summary and dynamic chronology metadata from this answer prompt. They are not independent evidence for a new factual answer, and excluding them reduces prefill as well as the opportunity to repeat an earlier hallucination. Original messages remain stored/searchable. A memory-selected answer retains the full budgeted conversation/summary/exact first anchor. This change covers the first planned site path; it does not claim that all possible later mixed memory/site refinements discard their current tool history.

The bounded final JSON wire format, 192-token planning allowance, 640-token answer allowance, 1–240 query bounds, existing pre-fusion metadata filters, canonical abstention, one-repair policy, cache telemetry, conditional native streaming/reset, and session isolation remain unchanged. A regression test confirms that a stored false Cursor claim and false summary are absent from a fresh site answer prompt but remain in the private archive; the existing conversation-summary test confirms history remains available to memory scope.
